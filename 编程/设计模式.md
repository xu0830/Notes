## 六大原则

### 单一职责原则

Single Responsibility Principle

一个类应该只负责一个职责



### 开闭原则

Open Closed Principle

对扩展开放，对修改关闭



### 里式替换原则

Liskov Substitution Principle

所有引用基类的地方必须能透明地使用其子类对象，能替换成子类



### 依赖倒置原则

Dependency Inversion Principle

高层模块不应该依赖底层模块，两者都应该依赖其抽象

面向抽象编程，而不是面向实现编程

#### 控制反转

获得依赖对象的过程被反转了

#### 依赖注入

##### 构造注入

###### 优点

直观，对其他类的依赖关系明显

脱离了IOC容器，这个类依然可以工作

###### 缺点

参数过多

无法使用默认构造函数

有些方法并不需要这些依赖

##### 属性注入

###### 优点

灵活， 可以随时动态地改变依赖

###### 缺点

设置依赖对象前对象的状态是不对的

不直观，无法清晰地表示哪些属性是必须的

##### 方法注入

###### 优点

灵活

###### 缺点

增加依赖需要修改原方法

### 接口隔离原则

Interface Segregation Principle

使用多个专门的接口，而不使用单一的总接口，客户端不应该依赖它不需要的接口



### 迪米特原则

Law of Demeter

一个软件实体应当尽可能少地与其他实体发生相互作用



## 设计模式



### 创建型

关注对象的创建，实例化对象的动作



#### 						         	单例模式

某个类只能有一个实例

自行创建类实例

自行向整个系统提供实例	

只执行一次构造函数

不重复实例化对象，会在内存中常驻一个对象实例

<font color='red'>反射破坏单例 ? </font> 去除无参构造函数

##### 实现方式

###### 饿汉式单例

1、静态构造函数（使用该类型前，.NET运行时调用且仅调用一次静态构造函数）

```c#
private Instance instance = null;

static Instance()
{
    instance = new Instance();
}
```

2、静态字段

```c#
private static Instance instance = new Instance();
```

###### 懒汉式单例

延迟加载，

1、双判断锁（线程安全）

```c#
if(instance == null)
{
	lock(obj)
    {
		if(instance == null)
        {
			instance = new Instance();
		}
	}
}
```

###### C#更优实现-饿汉式+懒汉式

```c#
public class Instance
{
    public static Instance GetInstance()
    {
     	return Nested.Instance;   
    }
    
    class Nested
    {
        static Nested(){}
        internal static readonly Instance Instance = new Instance();
    }
}
```

当第一次用到嵌套类型 Nested 的时候，会调用静态构造函数创建 Instance 的实例 instance，否则不会触发 CLR 

调用 Nested，也就不会创建实例，保证了延迟初始化

实现延迟加载，线程安全，不影响系统性能

##### 优点

1、封装了类的唯一实例，可以严格控制客户怎样以及何时访问它

2、只存在一个对象，避免频繁创建、销毁对象，节约系统资源，提高性能

3、基于单例模式，控制实例对象个数（数据库连接池、线程池）

##### 缺点

1、没有抽象层，扩展困难

2、单例类的职责过重，在一定程度上违背了单一职责的原创

单例类既提供了业务办法，又提供了创建对象的方法，对象的创建和业务耦合

3、实例化的共享对象长时间不使用，会被垃圾回收机制认为是垃圾，自动销毁和回收

##### 应用场景

线程池、数据库连接池、配置文件对象、IOC容器实例、缓存等



####          原型模式

Prototype Pattern

构造函数只执行一次，拷贝创建新对象实例

**继承 ICloneable 接口，实现 Clone 方法，调用 Object.MemberwiseClone ，创建浅拷贝副本**

##### 浅拷贝   

只对值类型,string 类型分配新的内存地址

复制引用类型的内存地址，指向堆内存的同一地址

```csharp
public class Resume : ICloneable
{
    private string name;
    
     public object Clone()
     {
         // 调用Object的MemberwiseClone()，创建当前object的浅表副本
         return MemberwiseClone() as Resume;
     }
}
public static void Main(string[] args)
{
    Resume a = new Resume("小李子");
    Resume b = a.Clone() as Resume;
}
```

##### 深拷贝

拷贝全新的对象

增加新的引用指针，指向新的内存地址

string 为引用类型，

深拷贝是因为拷贝出来的对象，若改变 string 的数据值，将重新分配内存地址

实现方法

反射

```c#
public static T DeepCopyByReflection<T>(T obj)
{
    if (obj is string || obj.GetType().IsValueType)
    {
        return obj;
    }

	object retval = Activator.CreateInstance(obj.GetType());

    FieldInfo[] fields = obj.GetType().GetFields(BindingFlags.Public | 
    	BindingFlags.NonPublic | BindingFlags.Static | BindingFlags.Instance);

    foreach (var field in fields)
    {
        try
        {
            //	迭代赋值
        	field.SetValue(retval, DeepCopyByReflection(field.GetValue(obj)));
        }
        catch{}
    }

    return (T)retval;
}
```

序列化反序列化（二进制、xml）

类特性注释<font color='red'>【Serializable】</font>

二进制

```c#
public static T DeepCopyByBinary<T>(T obj)
{
　　object retval;
　　using (MemoryStream ms = new MemoryStream())
　　{
　　　　BinaryFormatter bf = new BinaryFormatter();
　　　　bf.Serialize(ms, obj);
　　　　ms.Seek(0, SeekOrigin.Begin);
　　　　retval = bf.Deserialize(ms);
　　　　ms.Close();
　　}
　　return (T)retval;
}
```

xml

```c#
public static T DeepCopyByXml<T>(T obj)
{
　　object retval;
　　using (MemoryStream ms = new MemoryStream())
　　{
　　　　XmlSerializer xml=new XmlSerializer(typeof(T));
　　　　xml.Serialize(ms, obj);
　　　　ms.Seek(0, SeekOrigin.Begin);
　　　　retval = xml.Deserialize(ms);
　　　　ms.Close();
　　}
　　return (T)retval;
}
```

##### 优点

创建新对象实例较为复杂时，使用原型模式简化对象的创建过程

复制一个已有实例可以提高实例的创建效率

扩展性较好，通过抽象原型类，客户端可以针对抽象原型类编程，将具体实现类写在配置文件中，

可以通过深拷贝的方式保存对象的状态

##### 缺点

需要为每个类配备克隆方法 ，克隆方法位于类的内部，

对已有类进行改造时，需要修改源代码，违背了"开闭原则"

在实现深拷贝时需要编写较为复杂的代码，

当对象间存在多重嵌套引用时，每层对象对应的类都必须支持深拷贝

##### 应用场景

创建新对象成本较大（初始化需要占用较大的时间，占用太多的CPU资源或网络资源）



#### 简单工厂模式

将一个具体类的实例化交给一个静态工厂方法来执行，它不属于GOF的23种设计模式，但现实中却经常会用到

##### 优点

职责单一，实现简单，实现了客户代码与具体实现的解耦

##### 缺点

工厂类集中了所有实例的创建逻辑，将全部创建逻辑集中到了一个工厂类中，不利于维护和扩展

如果需要添加新的类，需要修改工厂类，违背开放封闭原则

##### 应用场景

工厂类负责创建的对象比较少



#### 工厂方法模式

Factory Method Pattern

定义一个用于创建对象的接口，让子类决定实例化哪一个类，类的实例化延迟到子类

核心工厂类不负责产品的创建，将具体的创建工作交给子类

**仅提供创建的接口，具体实现方法由继承的子类完成**

需要增加其他新的对象时，只需要添加一个具体的产品和它的创建工厂

不需要修改原工厂，很好地符合了“开闭原则”

```c#
public abstract FactoryBMW<BMW>{
}

public class FactoryBMW320 : FactoryBMW<BMW320>{  
}

public class FactoryBMW523 : FactoryBMW<FactoryBMW523>{
}


FactoryBMW320 factoryBMW320 = new FactoryBMW320();
BMW bmw320 = factoryBMW320.CreateBMW();

FactoryBMW523 factoryBMW523 = new FactoryBMW523();
BMW bmw523 = factoryBMW523.CreateBMW();

public abstract class BMW
{
}
public class BMW320 : BMW
{
    public BMW320()
    {
        Console.WriteLine("制造-->BMW320");
    }
}
public class BMW523 : BMW
{
    public BMW523()
    {
        Console.WriteLine("制造-->BMW523");
    }
}
```

##### 优点

去除了条件分支，解决了简单工厂模式对修改开放的问题

##### 缺点

客户端需要决定实例化哪个工厂来实现对具体产品的构建，选择判断依然存在，将简单工厂的逻辑判断交给客户端处理

##### 应用场景

子类数量不固定，随时可能有新的功能子类



#### 抽象工厂模式

Abstract Factory Pattern

封装创建接口，负责**创建一系列互相关联**的对象（产品簇）

用户使用时不需要指定对象所在的具体类

与工厂方法模式最大的区别在于，工厂方法模式针对的是一种产品的继承结构

抽象工厂模式需要面对多个产品的继承结构

```c#
public static void Main(String[] args)
{
    //生产宝马320系列配件
    FactoryBMW320 factoryBMW320 = new FactoryBMW320();
    factoryBMW320.CreateEngine();
    factoryBMW320.CreateTyre();

    //生产宝马523系列配件  
    FactoryBMW523 factoryBMW523 = new FactoryBMW523();
    factoryBMW320.CreateEngine();
    factoryBMW320.CreateTyre();
}
public interface AbstractFactory
{
    //制造发动机
    Engine CreateEngine();
    //制造轮胎 
    Tyre CreateTyre();
}
public class FactoryBMW320 : AbstractFactory
{
    public Engine CreateEngine()
    {
        return new EngineA();
    }
    public Tyre CreateTyre()
    {
        return new TyreA();
    }
}

// 宝马523系列生产配件
public class FactoryBMW523 : AbstractFactory
{
    public Engine CreateEngine()
    {
        return new EngineB();
    }
    public Tyre CreateTyre()
    {
        return new TyreB();
    }
}
```

##### 优点

具体产品从客户代码中分离出来

容易改变产品的系列

将一个系列的产品族统一到一起创建

##### 缺点

产品族中扩展新的产品困难，需要修改抽象工厂的接口

##### 应用场景

联合使用一系列相关产品对象

SqlClientFactory  ： DbProviderFactory 

  创建 DbConnection、DbCommand、DbDataAdapter、DbParameter



#### 建造者模式

Builder Pattern

将一个复杂对象（包含多个成员属性的对象）的构造与表示分离，使同样的构建过程可以创建不同的表示

与抽象工厂模式相似，建造者模式返回**一个完整的复杂产品**，抽象工厂模式返回**一系列相关的产品**

建造者 Builder（控制建造的抽象接口）



具体建造者 ConcreteBuilder（建造的具体细节实现）

指挥者 Director（指挥、构造使用建造者的对象，控制建造过程）

产品 Product（被构造的复杂对象）

```c#
public static void Main(String[] args)
{
    PersonDirector dir = new PersonDirector(new ThinPersonBuilder());
    Person person = dir.BuildPerson();
}
public class PersonDirector
{
     Builder builder;
     public PersonDirector(Builder personBuilder)
     {
         builder = personBuilder;
     }

     // 指挥创建一个人的过程，并返回创建成功的产品
     public Person BuildPerson()
     {
         builder.BuildHead();
         builder.BuildBody();
         builder.BuildArm();
         builder.BuildLeg();

         return builder.GetPerson();
     }
}
public abstract class Builder
{
    protected Person Person { get; set; }
    public Builder()
    {
        Person = new Person();
    }

    // 建造头
    public abstract void BuildHead();
    // 建造身体
    public abstract void BuildBody();
    // 建造胳膊
    public abstract void BuildArm();
    // 建造腿
    public abstract void BuildLeg();

    // 返回生成好的对象，这是一个具体方法，每个子类都可以使用它来返回一个已经创建成功的对象
    public Person GetPerson()
    {
        return Person;
    }
}
```

##### 优点

不需要知道具体的建造过程和细节

建造代码与表示分离

##### 缺点

扩展需要修改原代码，对修改开放

##### 应用场景

生成复杂结构对象

需要生成的产品对象的属性相互依赖，需要指定生成顺序

游戏开发中的开发角色管理系统、管理所有角色



### 结构型

关注类之间的关系

纵向关系： 继承、实现 （关系最紧密）

横向关系： 依赖、关联、聚合、组合

依赖：方法内部出现的类型

关联：以类的属性出现或引用了全局变量的类型，关系一般是平等的，如我和我的朋友

聚合：以类的属性出现或引用了全局变量的类型，整体和部分的关系（可分离），公司与员工

组合（强聚合）：以类的属性出现或引用了全局变量的类型， 

包含的关系，整体与部分（不可分离），人和人的大脑



#### 外观模式

Facade Pattern

为复杂的子系统提供一个统一的入口，定义了一个高层接口，使这一子系统更加容易使用

迪米特原则的一种具体实现

引入外观角色降低原有系统的复杂度，降低客户类与子系统的耦合

角色

外观类 Facade

子系统类 SubSystem

```
static void Main(string[] args)
{
	Facade facade = new Facade();
	facade.MethodA();
	facade.MethodB();
}

public class Facade
{
	private SubSystemOne one;
	private SubSystemTwo two;

    public Facade()
    {
        one = new SubSystemOne();
        two = new SubSystemTwo();
	}

	public void MethodA()
	{
    	Console.WriteLine("\nMethod group A----");
        one.MethodeOne();
        two.MethodTwo();
	}

    public void MethodB()
    {
        Console.WriteLine("\nMethod group B----");
        two.MethodTwo();
    }
}

public class SubSystemOne
{
	public void MethodeOne()
	{
		Console.WriteLine("Sub System first method.");
	}
}

public class SubSystemTwo
{
	public void MethodTwo()
	{
		Console.WriteLine("Sub System second method.");
	}
}
```

##### 优点

降低子系统使用的复杂性

松散客户端与子系统的耦合关系，更好的划分层次

##### 缺点

增加新子系统可能需要修改外观类或客户端代码，违背开闭原则

##### 应用场景

为复杂的子系统提供一个简单接口



#### 适配器模式

Adapter Pattern

将一个接口转换成客户端希望的另一个接口，使接口不兼容的类可以一起工作

适配器类继承需要的接口

```c#
static void Main(string[] args)
{
    IRobot dogRobot = new DogAdapter(new Dog());
    dogRobot.Talk();
    dogRobot.Move();
}
// 目标接口
public interface IRobot
{
	void Talk();
	void Move();
}
// 适配者：被适配的对象
public class Dog
{
    public void Talk(string name)
    {
        Console.WriteLine(name + ": 汪汪.....");
    }
    public void Move(string name)
    {
        Console.WriteLine(name + "快快跑......");
    }
}
// 适配器：它通过继承目标接口并维护一个适配者对象的引用，使二者关联起来
public class DogAdapter : IRobot
{
    private Dog dog;
    public DogAdapter(Dog dog)
    {
        //取得要适配的对象的引用
        this.dog = dog;
    }
    // 实现接口中的方法
    public void Talk()
    {
        dog.Talk("机器人");
    }
    public void Move()
    {
        dog.Move("机器人");
    }
}
```

##### 优点

将目标类和适配者类解耦，引入适配器类重用现有的适配者类，无需修改原有结构

增加类的透明性和复用性，将具体的业务实现过程封装在适配者类中，对于客户端是透明的

提高了适配者的复用性

灵活性和扩展性都非常好，在不修改原有代码的基础上增加新的适配器类，符合开闭原则

##### 缺点

在适配器中置换适配者类的某些方法比较麻烦

##### 应用场景

需要使用的现有类的接口不符合系统需要，甚至没有类的源代码

创建一个可以重复使用的类



#### 代理模式

Proxy Pattern

给某个对象提供一个代理，由代理对象来控制对原有对象的访问

```c#
static void Main(string[] args)
{
    BeautifulGirl mm = new BeautifulGirl("沈佳宜");
    Roommate roommate = new Roommate(mm);
    roommate.GiveFlowers();
}
public interface IGiveGift
{
	void GiveFlowers();
}
// RealSubject（真实对象）实现真正的业务逻辑
public class Boy : IGiveGift
{
	BeautifulGirl mm;     //美女
    public Boy(BeautifulGirl mm)
    {
    	this.mm = mm;
    }

    public void GiveFlowers()
    {
    	Console.WriteLine(mm.getName() + ",送你一束花....");
    }
}
// Proxy（代理对象）通过代理对象间接调用真实对象中定义的操作
public class Roommate : IGiveGift
{
	Boy boy;
    public Roommate(BeautifulGirl mm)
    {
	    boy = new Boy(mm);
    }
    public void GiveFlowers()
    {
        boy.GiveFlowers();
    }
}
public class BeautifulGirl
{
    string name;
    public BeautifulGirl(string name)
    {
    	this.name = name;
    }
}
```

##### 优点

隔离真正被调用的对象，降低系统的耦合度

保护目标对象，增加额外操作，如权限检查

##### 缺点

增加了代理对象，造成请求的处理速度变慢

实现代理类需要额外的工作，增加系统的实现复杂度

##### 应用场景

客户端对象需要访问远程主机中的对象

需要用消耗资源较少的对象来代表消耗资源较多的对象

需要控制对一个对象的访问，为不同用户提供不同级别的访问权限



#### 装饰模式

Decorator Pattern

可用于替代继承

动态将责任附加到对象上，扩展功能时比继承更加有弹性，

可以在不改变对象本身功能的基础上给对象增加额外的新行为

```c#
static void Main(string[] args)
{
	Component component = new Window();
	Component componentScrollBar = new ScrollBarDecorator(component);
	Component componentBlackBorder = new BlackBorderDecorator(componentScrollBar);
	componentScrollBar.Display();
}
public abstract class Component
{
    public abstract void Display();
}
public class Window : Component
{
    public override void Display()
    {
        Console.WriteLine("显示窗体！");
    }
}
public class ComponentDecorator : Component
{
    private Component component;  //维持对抽象构件类型对象的引用
    public ComponentDecorator(Component component)  //注入抽象构件类型的对象
    {
        this.component = component;
    }
    public override void Display()
    {
        component.Display();
    }
}
public class ScrollBarDecorator : ComponentDecorator
{
    public ScrollBarDecorator(Component component) : base(component)
    {
    }
    public override void Display()
    {
        this.SetScrollBar();
        base.Display();
    }
    public void SetScrollBar()
    {
        Console.WriteLine("为构件增加滚动条！");
    }
}
```

##### 优点

对于扩展一个对象的功能，比继承更加灵活，不会导致类的个数急剧增加

动态扩展对象的功能，通过配置文件可以在运行时选择不同的具体装饰类

多次装饰，可以创造不同行为的组合

可以根据需要增加新的具体构建类和具体装饰类，原有类代码无需改变，符合开闭原则

##### 缺点

过度使用会增加复杂度

比继承更易于出错，排错困难

##### 应用场景

在不影响其他对象的情况下，以动态、透明的方式给单个对象添加职责

不能采用继承的方式扩展系统，类存在大量独立的扩展或类被定义为不能继承 （Sealed）

采用继承不利于系统扩展和维护时



#### 桥接模式

Bridge Pattern

分离抽象部分与实现部分，使它们可以独立变化

两个类型都有自己的多类实现

将实现部分的变化封装到另外的类

```c#

	Shape square = new Square();
	square.SetColor(white);
	square.Draw();

    rectange.SetColor(white);
    rectange.Draw();

    public Color color;
    public void SetColor(Color color)
    {
        this.color = color;
    }

    public override void Draw()

    }

public class Square : Shape
{
    public override void Draw()
    {
        color.Bepaint("正方形");
    }
}

{
    void Bepaint(string shape);
}
public class White : Color
{
    public void Bepaint(string shape)

}
public class Gray : Color
{
    public void Bepaint(string shape)
```

##### 优点

抽象与实现解耦

抽象与实现可以独立扩展，不需要修改原有系统

细节对客户端透明，隐藏具体实现细节

##### 缺点

增加系统的复杂度

##### 应用场景

增加抽象与实现性灵活性



#### 组合模式

组合多个对象形成树形结构，表示整体-部分关系

定义抽象组件类，既可以代表叶子，又可以代表容器

#### 享元模式

Flyweight Pattern

解决对象复用，提供第三方的管理，共享对象

内部状态：在享元对象内部并且不会随着环境的改变而改变的共享部分

外部状态：随环境改变而改变，不可以共享的状态

可自行实例化对象，不像单例是强制保证

核心在于享元工厂类，提供一个用于存储享元对象的享元池，

用户需要对象时，先从享元池中获取，不存在时创建并保存

池化资源管理

```c#
public static void Main(string[] args)
{
    // 定义外部状态，例如字母的位置等信息
    int externalstate = 10;
    // 初始化享元工厂
    var factory = new FlyweightFactory();

    // 判断是否已经创建了字母A，如果已经创建就直接使用创建的对象A
    Flyweight fa = factory.GetFlyweight("A");
    if (fa != null)
    {
        // 把外部状态作为享元对象的方法调用参数
        fa.Operation(--externalstate);
    }
    // 判断是否已经创建了字母B
    Flyweight fb = factory.GetFlyweight("B");
    if (fb != null)
    {
        fb.Operation(--externalstate);
    }
    // 判断是否已经创建了字母C
    Flyweight fc = factory.GetFlyweight("C");
    if (fc != null)
    {
        fc.Operation(--externalstate);
    }
    // 判断是否已经创建了字母D
    Flyweight fd = factory.GetFlyweight("D");
    if (fd != null)
    {
        fd.Operation(--externalstate);
    }
    else
    {
        Console.WriteLine("驻留池中不存在字符串D");
        // 这时候就需要创建一个对象并放入驻留池中
        var d = new ConcreteFlyweight("D");
        factory.Flyweights.Add("D", d);
    }
}
public class FlyweightFactory
{
    // 享元池
    public Dictionary<string, Flyweight> flyweights = new Dictionary<string, Flyweight>();
    public FlyweightFactory()
    {
        Flyweights.Add("A", new ConcreteFlyweight("A"));
        Flyweights.Add("B", new ConcreteFlyweight("B"));
        Flyweights.Add("C", new ConcreteFlyweight("C"));
    }

    public Flyweight GetFlyweight(string key)
    {
        Flyweight flyweight = flyweights[key] as Flyweight;
        if (flyweight == null)
        {
         	Console.WriteLine("驻留池中不存在字符串" + key);
            flyweight = new ConcreteFlyweight(key);
        }
        return flyweight;
    }
}
//	抽象享元类
public abstract class Flyweight
{
    public abstract void Operation(int extrinsicstate);
}
public class ConcreteFlyweight : Flyweight
{
    // 内部状态
    private readonly string _intrinsicstate;

    // 构造函数
    public ConcreteFlyweight(string innerState)
    {
        this._intrinsicstate = innerState;
    }

    /// <summary>
    /// 享元类的实例方法
    /// </summary>
    /// <param name="extrinsicstate">外部状态</param>
    public override void Operation(int extrinsicstate)
    {
        Console.WriteLine("具体实现类: intrinsicstate {0}, extrinsicstate {1}", _intrinsicstate, extrinsicstate);
    }
}
```

##### 优点

能极大减少系统中对象的个数，相同或相似对象在内存中只保存一份，节约系统资源

使用了相对独立的外部状态，不会影响到内部状态，使享元对象能够在不同的环境被共享

##### 缺点

需要区分外部状态和内部状态，系统更复杂

为使对象可以共享，需要将享元对象的状态外部化，读取外部状态使得运行时间更长

##### 应用场景

系统中存在大量相同或相似对象

对象的大部分状态可以外部化，可以将这些外部状态传入对象中

#### 模板方法模式

Template Method Pattern

某个方法的实现需要多个步骤，有些步骤是固定的，有些步骤不固定

定义操作中的框架，将一些步骤延迟到子类，子类不改变操作的结构的前提下，重定义某些特定步骤

钩子，声明在抽象类中的空方法或默认实现

```c#
static void Main(string[] args)
{
    CoffeeWithHook coffeeHook = new CoffeeWithHook();
    coffeeHook.MakeDrink();
}
public abstract class DrinkWithHook
{
    public void MakeDrink()
    {
        BoilWater();
        BrewDrink();
        PourInCup();
        //如果顾客需要添加调料，我们才会调用addCondiments()方法
        if (IsCustomerWantCondiments())
        {
            AddCondiments();
        }
    }
    // 冲泡饮料
    public abstract void BrewDrink();
    // 添加调料
    public abstract void AddCondiments();
    private void BoilWater()
    {
        Console.WriteLine("Boiling water...");
    }
    private void PourInCup()
    {
        Console.WriteLine("Pouring into Cup...");
    }
    public virtual bool IsCustomerWantCondiments()
    {
        return true;
    }
}
public class CoffeeWithHook : DrinkWithHook
{
    // 覆盖该钩子，提供自己的实现方法
    public override bool IsCustomerWantCondiments()
    {
        if ("y".Equals(GetUserInput().ToLower()))
        {
            return true;
        }
        else
        {
            return false;
        }
    }

    public string GetUserInput()
    {
        Console.WriteLine("Would you like some milk and sugar(y/n):");
        string answer = Console.ReadLine();
        if (string.IsNullOrEmpty(answer) || (!answer.Equals("y") && !answer.Equals("n")))
        {
            return "n";
        }
        return answer;
    }

    public override void BrewDrink()
    {
        Console.WriteLine("Dripping Coffee through filter...");
    }

    public override void AddCondiments()
    {
        Console.WriteLine("Adding Sugar and Milk...");
    }
}
```

##### 优点

代码复用，父类提取类的公共行为，通过子类实现不同的行为

实现反向控制，通过子类覆盖父类的钩子方法来决定某一个特定步骤是否执行

子类覆盖父类的基本方法，更换、增加新子类很方便，符合单一职责原则和开闭原则

##### 缺点

每一个不同的实现需要一个子类实现，导致类的个数增加，系统更庞大

<font color='red'>可结合桥接模式进行设计</font>

##### 应用场景

分割复杂算法，算法固定部分设计为模板方法，可变细节由子类实现

提取子类公共行为到父类，复用代码

通过子类决定父类算法中某个步骤是否执行，实现子类对父类的反向控制



#### 观察者模式

Observer Pattern

定义对象间的一对多依赖关系，当一个对象状态发生改变时，相关依赖对象得到通知并自动更新

别名：发布-订阅、模型-视图、源-监听器、从属者

```c#
public static void Main(string[] args)
{
    //定义观察目标对象
    Team acc = new ConcreteTeam("金庸群侠");
    //定义四个观察者对象
    IObserver player1, player2, player3, player4;
    player1 = new Player("杨过");
    acc.Register(player1);
    //某成员遭受攻击
    player1.BeAttacked(acc);
}
// 抽象观察类
public interface IObserver
{
    string GetName();
    void Help(); //声明支援盟友方法
    void BeAttacked(Team acc); //声明遭受攻击方法
}
// 战队成员类：具体观察者类
public class Player : IObserver
{
    private string name;

    public Player(string name)
    {
        this.name = name;
    }

    public string GetName()
    {
        return name;
    }

    // 支援盟友方法的实现
    public void Help()
    {
        Console.WriteLine("坚持住，" + name + "马上来救你！");
    }

    // 遭受攻击方法的实现，当遭受攻击时将调用战队类的通知方法NotifyObserver()来通知盟友
    public void BeAttacked(Team acc)
    {
        Console.WriteLine(name + "被攻击！");
        acc.NotifyObserver(name);
    }
}
// 战队：抽象目标类
public abstract class Team
{
    protected string teamName; //战队名称
    protected List<IObserver> players = new List<IObserver>(); //定义一个集合用于存储战队成员

    public void SetTeamName(string teamName)
    {
        this.teamName = teamName;
    }
    public string GetTeamName()
    {
        return teamName;
    }
    // 注册方法
    public void Register(IObserver obs)
    {
        Console.WriteLine(obs.GetName() + "加入" + teamName + "战队！");
        players.Add(obs);
    }
    // 注销方法
    public void Remove(IObserver obs)
    {
        Console.WriteLine(obs.GetName() + "退出" + teamName + "战队！");
        players.Remove(obs);
    }

    // 声明抽象通知方法
    public abstract void NotifyObserver(string name);
}
// 具体战队类：具体目标类
public class ConcreteTeam : Team
{
    public ConcreteTeam(string teamName)
    {
        Console.WriteLine(teamName + "战队组建成功！");
        Console.WriteLine("----------------------------");
        this.teamName = teamName;
    }

    // 实现通知方法
    public override void NotifyObserver(string name)
    {
        Console.WriteLine(teamName + "战队紧急通知，盟友" + name + "遭受敌人攻击！");
        // 遍历观察者集合，调用每一个盟友（自己除外）的支援方法
        foreach (var obs in players)
        {
            if (!(obs.GetName().Equals(name, StringComparison.CurrentCultureIgnoreCase)))
            {
                obs.Help();
            }
        }
    }
}
```

##### 优点

在观察对象和观察者间建立抽象的耦合，观察目标只需要维护一个抽象观察者的集合，无需了解具体观察者

支持广播通信，向所有的观察者发出通知

符合开闭原则，增加新的具体观察者无需修改原有代码

##### 缺点

观察者过多，通知耗时长

观察者和观察目标有循环依赖，观察目标会触发循环调用，可能导致系统崩溃

没有响应的机制让观察者知道所观察的目标对象是怎么发生变化，仅知道发生变化

##### 应用场景

创建链式触发机制

对象的改变需要改变其他对象，具体对象不清楚

AOP https://www.cnblogs.com/idior/articles/229590.html



#### 状态模式

State Pattern

允许一个对象在其内部状态改变时改变它的行为

当控制一个对象状态转换的条件过于复杂，把状态的判断逻辑转移到表示不同状态的一系列类中，

把复杂的逻辑判断简单化

```c#
static void Main(string[] args)
{
    // 设置Context的初始状态为ConcreteStateA
    Context context = new Context(new ConcreteStateA());
    // 不断地进行请求，同时更改状态
    context.Request();
    context.Request();
    context.Request();
    context.Request();
}
public class Context
{
    public Context(State state)
    {
        this.state = state;
    }
    public State State { get; set; } 
    /// <summary>
    /// 对请求做处理，并设置下一个状态
    /// </summary>
    public void Request()
    {
        state.Handle(this);
    }
}
public abstract class State
{
    public abstract void Handle(Context context);
}
public class ConcreteStateA : State
{
    /// <summary>
    /// 设置ConcreteStateA的下一个状态是ConcreteStateB
    /// </summary>
    /// <param name="context"></param>
    public override void Handle(Context context)
    {
        Console.WriteLine("当前状态是 A.");
        context.State = new ConcreteStateB();
    }
}
public class ConcreteStateB : State
{
    /// <summary>
    /// 设置ConcreteStateB的下一个状态是ConcreteSateA
    /// </summary>
    /// <param name="context"></param>
    public override void Handle(Context context)
    {
        Console.WriteLine("当前状态是 B.");
        context.State = new ConcreteStateA();
    }
}
```

##### 优点

将特定状态相关的行为局部化，并且将不同状态的行为分割开

与状态相关的代码都存在于某个 Concrete State 中，通过定义新的子类很容易将增加新的状态和转换

把状态转移逻辑分到State的子类中，减少依赖

##### 缺点

导致较多的 Concrete State 子类

##### 应用场景

当一个对象的行为取决于状态，并且必须在运行时根据状态改变行为

操作中含有庞大的分支结构，且这些分支决定于对象的状态



#### 职责链模式

Chain of Responsibility Pattern

避免请求发送者与接收者耦合在一起，让多个对象都有可能接收请求

将处理对象连接成一条链，沿着链传递请求，直到有对象处理它为止

```c#
public static void Main(string[] args)
{
    Handler wjzhang, gyang, jguo, meeting;
    wjzhang = new Director("张无忌");
    gyang = new VicePresident("杨过");
    jguo = new President("郭靖");
    meeting = new Congress("董事会");
    //创建职责链
    wjzhang.SetSuccessor(gyang);
    gyang.SetSuccessor(jguo);
    jguo.SetSuccessor(meeting);
    //创建采购单
    PurchaseRequest pr1 = new PurchaseRequest(45000, 10001, "购买倚天剑");
    wjzhang.ProcessRequest(pr1);
    PurchaseRequest pr2 = new PurchaseRequest(90000, 10002, "购买《九阳真经》残章");
    wjzhang.ProcessRequest(pr2);
    PurchaseRequest pr3 = new PurchaseRequest(160000, 10003, "购买《九阴真经》");
    wjzhang.ProcessRequest(pr3);
    PurchaseRequest pr4 = new PurchaseRequest(800000, 10004, "购买桃花岛");
    wjzhang.ProcessRequest(pr4);
}

{
    private double amount;  //采购金额
    private int number;  //采购单编号
    private string purpose;  //采购目的
    public PurchaseRequest(double amount, int number, string purpose)
    {
        this.amount = amount;
        this.number = number;
        this.purpose = purpose;
    }
    public double Amount
    {
        set { amount = value; }
        get { return amount; }
    }
    public int Number
    {
        get { return number; }
        set { number = value; }
    }
    public string Purpose
    {
        get { return purpose; }
        set { purpose = value; }
    }
}
public abstract class Handler
{
    protected Handler m_Successor; //定义后继对象
    protected string m_Name; //审批者姓名
    public Handler(string name)
    {
        this.m_Name = name;
    }
    //设置后继者
    public void SetSuccessor(Handler successor)
    {
        this.m_Successor = successor;
    }
    //抽象请求处理方法
    public abstract void ProcessRequest(PurchaseRequest request);
}

}

        }
        else
        {
            this.m_Successor.ProcessRequest(request);  //转发请求
        }
    }
}

//董事长类：具体处理者
public class President : Handler
{

    {
    }
```

##### 优点

降低耦合度，将请求的发送者和接收者解耦

简化了对象，使对象不需要知道链的结构

增强给对象指派职责的灵活性，改变链内的成员或者次序，允许动态新增或者删除责任

增加新的请求处理类很方便

##### 缺点

不能保证请求一定被接收

系统性能将收到一定影响，代码调试不太方便，可能造成循环调用

不容易观察运行时的特征，不易排错

##### 应用场景

多个对象处理同一个请求，具体处理对象由运行时自动确定

在不明确指定接收者的情况下，向多个对象的一个提交请求

动态指定一组对象处理请求



#### 命令模式

Coommand Pattern

将一个请求封装为一个对象，用不同的请求对客户进行参数化

本质在于对命令进行封装，将发出命令的责任和执行命令的责任分开

```C#
public static void Main(string[] args)
{
    var r = new Receiver();
    Command c = new ConcreteCommand(r);
    var i = new Invoker();
    i.SetCommand(c);
    i.ExecuteCommand();
}
abstract class Command
{
    // Fields 
    protected Receiver Receiver;

    // Constructors 
    protected Command(Receiver receiver)
    {
        this.Receiver = receiver;
    }

    // Methods
```

##### 缺点

增加新的元素类困难，在访问者模式中，每增加一个新的元素类都意味着要在抽象访问者角色中增加一个新的抽象操作，

不同类型的对象可以有不同的访问操作

对象结构中对象对应的类很少改变，但经常需要在此对象结构上定义新的操作

#### 解释器模式

Interpreter Pattern

定义一个语言的语法，并且建立一个解释器来解释该语言的句子

角色

抽象表达式 AbstractExpression

终结符表达式 TerminalExpression

非终结符表达式 NonterminalExpression

上下文 Context

```c#
public static void Main(string[] args)
{
    string instruction = "up move 5 and down run 10 and left move 5";
    InstructionHandler handler = new InstructionHandler();
    handler.Handle(instruction);
    string outString;
    outString = handler.Output();
    Console.WriteLine(outString);
}
//指令处理类：工具类
public class InstructionHandler
{
    private AbstractNode node;
    public void Handle(string instruction)
    {
        AbstractNode left = null, right = null;
        AbstractNode direction = null, action = null, distance = null;
        Stack stack = new Stack(); //声明一个栈对象用于存储抽象语法树
        string[] words = instruction.Split(' '); //以空格分隔指令字符串
        for (int i = 0; i < words.Length; i++)
        {
            // 本实例采用栈的方式来处理指令，如果遇到“and”，
            // 则将其后的三个单词作为三个终结符表达式连成一个简单句子SentenceNode,
            // 作为“and”的右表达式，而将从栈顶弹出的表达式作为“and”的左表达式，
            // 最后将新的“and”表达式压入栈中。    		        
            if (words[i].Equals("and", StringComparison.CurrentCultureIgnoreCase))
            {
                left = (AbstractNode)stack.Pop(); //弹出栈顶表达式作为左表达式
                string word1 = words[++i];
                direction = new DirectionNode(word1);
                string word2 = words[++i];
                action = new ActionNode(word2);
                string word3 = words[++i];
                distance = new DistanceNode(word3);
                right = new SentenceNode(direction, action, distance); //右表达式
                stack.Push(new AndNode(left, right)); //将新表达式压入栈中
            }
            //如果是从头开始进行解释，则将前三个单词组成一个简单句子SentenceNode并将该句子压入栈中
            else
            {
                string word1 = words[i];
                direction = new DirectionNode(word1);
                string word2 = words[++i];
                action = new ActionNode(word2);
                string word3 = words[++i];
                distance = new DistanceNode(word3);
                left = new SentenceNode(direction, action, distance);
                stack.Push(left); //将新表达式压入栈中
            }
        }
        this.node = (AbstractNode)stack.Pop(); //将全部表达式从栈中弹出
    }

    public string Output()
    {
        string result = node.Interpret(); //解释表达式
        return result;
    }
}
//抽象表达式
public abstract class AbstractNode
{
    public abstract string Interpret();
}
//And解释：非终结符表达式
public class AndNode : AbstractNode
{
    private AbstractNode left; //And的左表达式
    private AbstractNode right; //And的右表达式
    public AndNode(AbstractNode left, AbstractNode right)
    {
        this.left = left;
        this.right = right;
    }
    //And 达式解释操作
    public override string Interpret()
    {
        return left.Interpret() + ", 再" + right.Interpret();
    }
}
//简单句子解释：非终结符表达式
public class SentenceNode : AbstractNode
{
    private AbstractNode direction;
    private AbstractNode action;
    private AbstractNode distance;

    public SentenceNode(AbstractNode direction, AbstractNode action, AbstractNode distance)
    {
        this.direction = direction;
        this.action = action;
        this.distance = distance;
    }
    //简单句子的解释操作
    public override string Interpret()
    {
        return direction.Interpret() + action.Interpret() + distance.Interpret();
    }
}
//方向解释：终结符表达式
public class DirectionNode : AbstractNode

    public DirectionNode(string direction)
    {
        this.direction = direction;
    }
    //方向表达式的解释操作
    public override string Interpret()
    {
        if (direction.Equals("up", StringComparison.CurrentCultureIgnoreCase))
        {
            return "向上";
        }
        else if (direction.Equals("down", StringComparison.CurrentCultureIgnoreCase))
        {
            return "向下";
        }
        else if (direction.Equals("left", StringComparison.CurrentCultureIgnoreCase))
        {
            return "向左";
        }
        else if (direction.Equals("right", StringComparison.CurrentCultureIgnoreCase))
        {
            return "向右";
        }
        else
        {
            return "无效指令";
        }
    }
}
```

##### 优点

##### 缺点
