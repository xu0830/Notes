## 同步

## 异步

在返回调用者之后去做它的（大部分）工作

### 异步编程

原则是将长时间运行的函数写成异步的

#### 用途

- 编写高效处理大量并发 IO 的应用程序（服务器端应用，关键是执行效率，每个网络请求并不会消耗一个线程）

- 富客户端应用，简化线程安全，长时间操作必须运行在 worker 线程上，保证 UI 响应  


IO 操作的 DMA （Direct Memory Access）模式，直接内存访问，

不经过 CPU 就可以直接访问内存数据的一种数据交换模式

DMA 模式的数据交互几乎不耗 CPU 资源（硬盘、声卡、显卡、网卡等都具有 DMA 功能）

CLR 所提供的异步编程模型就是让我们充分利用硬件 DMA 功能来转移 CPU 的压力

底层使用线程池管理，开始IO操作时，异步会把工作线程还给线程池，线程操作不再占用 CPU 资源

**CPU 密集型采用多线程** 

**IO 密集型采用异步**

涉及到任何读写操作和数据传输的，就属于 IO 密集型，否则就是 CPU 密集型

### Sleep

<font color='red'>Thread.Sleep(0)</font> 

这样调用会导致线程立即放弃本身当前的时间片，自动将CPU移交给其他的线程

Thread.Yield() 做同样事情，但是它只会把执行交给同一处理器上的其他线程

### 阻塞

如果线程的执行由于某种原因导致暂定，那么就认为该线程被阻塞了 (sleep() join())

被阻塞的线程会立即将其处理器的时间片生成给其他线程，不再消耗处理器时间，直到满足其阻塞条件为止

通过 ThreadState 属性判断线程是否处于被阻塞状态 

(主要属性 Unstarted、Running、WaitSleepJoin、 Stopped )

```c#
bool blocker = (someThread.ThreadState & ThreadState.WaitSleepJoin) != 0
```

### 解除阻塞

满足阻塞条件

操作超时（如果设置超时的话）

Thread.Interrupt（）进行打断

Thread.Abort（）进行中止

### 上下文切换

当线程阻塞或解除阻塞时，操作系统将执行上下文切换，会产生少量开销，通常为1或2微秒

### 前台线程 / 后台线程

IsBackground 属性设置、判断

默认情况下，手动创建的线程就是前台线程

只要有前台线程在运行，那么应用程序就会一直处于活动状态，后台线程不行

所有的前台线程停止，应用程序就停止了，所有的后台线程也会停止

前台、后台状态与它的优先级无关（所分配的执行时间）

进程以这种形式终止的时候，后台线程执行栈中的 finally 块就不会被执行

如果想让它执行。可在退出程序时使用 Join 等待后台线程（自己创建的线程）

或者使用 signal construct （线程池）

应用程序无法正常退出的一个常见原因是还有活跃的前台线程

## UI客户端程序的线程

在主线程（UI线程）执行耗时操作，会导致整个程序无响应

因为主线程同时还需要处理消息循环，渲染、鼠标、键盘事件处理等工作都是消息循环来执行的

耗时操作，启用一个 worker 线程

执行完操作后，再更新到 UI

线程模式通常是

​	UI元素和控件只能从创建它们的线程来访问（通常是主UI线程）

​	当想从 worker 线程更新 UI 的时候，把请求交给 UI 线程
底层实现

WPF，元素的 Dispatcher 对象上调用 BeginInvoke 或 Invoke

WinForm， 调用空间的 BeginInvoke 或 Invoke 

UWP，调用 Dispatcher 对象上的 RunAsync 或 Invoke

所有这些方法都接收一个委托

BeginInvoke 或 RunAsync 通过将委托排队到 UI线程的消息队列来执行工作

Invoke 执行相同的操作，但随后会进行阻塞，直到 UI 线程读取并处理消息，因此

Invoke 允许从方法中获取返回值

不需要返回值，BeginInvoke / RunAsync 更可取，因为它们不会阻塞调用方，

也不会引入死锁的可能性 


### 线程池中的整洁

确保临时超出 计算-Bound 的工作不会导致 CPU 超额订阅

CPU 超额订阅： 活跃的线程超过 CPU 的核数，操作系统就需要对线程进行时间切片

超额订阅对性能影响很大，时间切片需要昂贵的上下文切换，并且可能使 CPU 缓存失效

CPU 缓存对于现代处理器的性能至关重要

### CLR的策略

通过对任务排队并对其启动进行节流限制来避免线程池中的超额订阅

首先运行尽可能多的并发任务（只要还有 CPU 核），然后通过爬山算法调整并发级别，

并在特定方向上不断调整工作负载（如果吞吐量提高，它将继续朝同一方向，否则反转）

确保它始终追随最佳性能曲线，即使面对计算机上竞争的进程活动时也是如此

CLR策略发挥最佳效果，需满足

​		工作项大多是短时间运行的 （<250毫秒，或者理想情况下 < 100毫秒，

​		因此CLR有很多机会进行测量和调整

​		大部分时间都被阻塞的工作项不会主宰线程池

## Task

线程是用来创建并发（concurrency）的一种低级别工具，它的限制：

​	虽然开始线程的时候可以方便的传入数据，但是当 Join 的时候，很难从线程获得返回值

​		可能需要设置一些共享字段

​		捕获、传播异常很麻烦

​	无法告诉线程在结束时开始做另外的工作，必须进行 Join 操作 （在进程中阻塞当前线程）

​	很难使用较小的并发来组建大型的并发 

Task 类 可以很好的解决上述问题

相对高级的抽象：代表了一个并发操作，操作可能由 Thread 支持 或不由 Thread 支持

可组合， 可使用Continuation 把它们串成链

可使用线程池减少启动延迟

默认使用线程池，也就是后台线程

### Long-running tasks

默认情况下，CLR 在线程池中运行 Task， 这非常适合短时间运行的 Compute-Bound 类工作

针对长时间运行的任务或者阻塞操作，可不采用线程池

```c#

	Thread.Sleep(3000);

```

如果同时运行多个long-running tasks （尤其是其中有处于阻塞状态的），那么性能将会受很大影响

如果任务是IO-Bound，TaskCompletionSource 和异步函数可以让你用回调代替线程来实现并发

如果任务是Compute-Bound，生产者/消费者队列运行对任务的并发性进行限流，避免把其他线程和进程饿死

### 异常

task里面抛出了未处理异常，异常就会重新抛出给

​	调用了 wait（） 的地方

​	访问了 Task<TResult> 的 Result 属性的地方

CLR 会将异常包裹在 AggregateException 里， 以便在并行编程场景中发挥很好的作用

```
Task task = Task.Run(() => { throw null;});
try
{
	task.Wait();
}
catch(AggregateException aex)
{
	if(aex.InnerException is NullReferenceException)
	{
		Console.WriteLine("Null");
	}
	else
	{
		throw;
	}
}
```

无需重新抛出异常，通过 Task 的 IsFaulted 和 IsCanceled 属性也可以检测出 Task 是否发生了故障

​	两个属性都返回了false，无错误发生

​	 IsCanceled 为 true，说明一个 OperationCancelExcception 为该 Task 抛出了

​	 IsFaulted 为 true，说明另一个类型的异常被抛出了，Exception 属性也指明错误 

可通过全局 TaskScheduler.UnobservedTaskException 订阅未观察到的异常

### TaskCompletionSource

在稍后开始和结束的任意操作中创建 Task

​	提供一个可手动执行的“从属”Task“

​		指示操作何时结束或发生故障

​	对 IO-Bound 类工作比较理想

​		可以获得所有 Task 的好处（传播值、异常、Continuation等）

创建线程，但不占用线程 

```C#
var tsc = new TaskCompletionSource<int>();
new Thread(() =>
{
	Thread.Sleep(5000);
	tcs.SetResult(42);
})
{
	IsBackground = true;    
};
Task<int> task = tcs.Task;
Console.WriteLine(task.Result);
```

### await

异步

简化了附加 continuation 的过程

```c#
//结构
var result = await expression;
statement(s)；

//	等价于
var awaiter = expression.GetAwaiter();
awaiter.OnCompleted(() => 
{
	var result = awaiter.GetResult();
    statement(s);	
});
```

遇到 await 表达式，执行（正常情况下）会返回调用者

​	就像 iterator 里面的 yield return

​	在返回前，运行时会附加一个 continuation 到 await 的 task

​		为保证 task 结束时，执行会跳回原方法，从停止的地方继续执行

​	发生故障，异常会被重新抛出

​	正常则返回值会赋给 await 表达式

可用await

await task 表达式 

满足下列条件的对象

​	有GetAwaiter（）方法，返回一个 awaiter （实现了 INotifyCompletion.OnCompleted  接口）

​	返回适当类型的GetResult（）

​	一个 bool 类型的 IsCompleted 属性

在异步方法内，await表达式可以替换任何表达式

​	除了 lock 表达式 和 unsafe 上下文

#### await 之后在哪个线程执行

await 表达式后，编译器依赖于 continuation 来继续执行

​	UI客户端程序，同步上下文会保证后续是在原线程上执行

​	否则，就在 Task 结束的线程上继续执行
