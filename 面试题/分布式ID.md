# 分布式 ID

分库分表后的全局唯一 ID

## 条件

- 全局唯一
- 高性能
- 高可用
- 好接入，尽可能简单

## 方式

- UUID
- 数据库自增 ID
- 数据库多主模式
- 号段模式
- Redis 
- 雪花算法（SnowFlake）
- 滴滴出品（TinyID）
- 百度（Uidgenerator）
- 美团（Leaf）

### 基于UUID

不适用于实际的业务需求，订单号一般需要含有用信息

#### 优点

- 简单，本地生成无网络消耗

#### 缺点

- 没有具体的业务含义
- 长度过长，数据库存储及查询的性能消耗较大，无序性不利于索引，会导致数据位置频繁变动，严重影响性能

### 基于数据库自增 ID

用一个单独的数据库实例来生成 ID，插入记录后返回主键 ID

#### 优点

- 实现简单，数值类型查询速度快

#### 缺点

- DB单点存在宕机风险，无法抗住高并发场景，访问量激增时数据库本身就是系统的瓶颈，用它来实现分布式服务风险较大

### 基于数据库集群模式

数据库采用主从集群模式，或者双主模式集群，两个数据库实例都能单独生产自增 ID

解决方案：设置起始值和自增步长，**自增步长按照机器数量来设置**

Mysql_1 起始值 1 步长 2，生成奇数 ID

Mysql_2 起始值 2 步长 2，生成偶数 ID

如果集群后的性能还是扛不住高并发时，还要进行 MySql 扩容增加节点

#### 基于数据库的号段模式

主流实现方式之一

从数据库批量获取自增ID，每次从数据库取出一个号段范围，如1-1000，生成自增 ID 并加载到内存中使用

一批号段 ID 用完，再次向数据库申请新号段，更新 max_id 字段， update max_id = max_id + step，更新成功说明获取新号段成功，新的号段范围是（max_id, max_id + step）

```
update id_generator set max_id = #{max_id+step}, version = version + 1 where version = # {version} and biz_type = XXX
```

由于可能出现同时操作，所以采用版本号 version 乐观锁方式更新。

不强依赖于数据库，不会频繁的访问数据库，对数据库的压力小很多

### 基于Redis模式

利用 redis 的 incr 命令实现 ID 的原子性自增

需要考虑 redis 持久化的问题

- RDB 定时执行快照持久化，当连续自增但 redis 没及时持久化，如果 redis 宕机，重启 redis 会出现 ID 重复的情况
- AOF 会对每条写命令进行持久化 ，即使 redis 挂掉也不会出现 ID 重复问题，但由于 incr 命令的特殊性，会导致 redis 重启恢复的时间过长

### 基于雪花算法

snowflake 生成的是 long 类型的 ID，占 8 个字节，64 bit

组成结构

符号位（1 bit） +  时间戳 （41 bit）+  机器 ID （5 bit） +  数据中心 （5 bit） + 自增值 （12 bit）

- 第一个 bit 位，正数为 0，负数为 1，默认为0
- 时间戳部分，毫秒级，不建议存当前时间，而是用当前时间戳与固定开始时间戳的差值，可以使产生的 ID 从更小的值开始；41 位的时间戳可以使用 69年，2^41 /（ 1000 * 60 * 60 * 24 * 365）= 69
- 机器 id，也被叫做  workId，可以灵活配置，机房或者机器号组合都可以
- 序列化部分，自增值支持同一毫秒内同一个节点生成 4096 个 ID

只需保证每个业务应用有自己的机器 id 即可

### 百度（uid-generator）

基于 snowflake 算法实现

自定义时间戳、机器 ID 和 序列化等各部分的位数

采用用户自定义 workId 的生成策略
